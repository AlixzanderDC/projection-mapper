# How projection-mapping software is built and used — research notes for skill authoring

Compiled 2026-10-23 from official docs, repository READMEs and source files read online (no repos downloaded). Everything marked **[unverified]** could not be confirmed from a primary source during this pass. Items marked **[mirror]** were read from a third-party GitHub mirror of a GitLab project and may lag the canonical tree.

Scope reminder: the user's own tool is a browser WebGL2 mapper (corner-pin + warp-grid surfaces, masks, per-edge blend ramps, multi-window outputs synced over BroadcastChannel, camera-assisted mapping, a sphere mode for three projectors around a 60-inch inflatable moon). The point of this document is what the *field* does, so an agent can teach the professional workflow and point at working code.

## 1. Open-source mappers, commercial tools and libraries: architecture and where to read

### 1.1 Splash (SAT Metalab) — the reference open-source multi-projector 3D mapper

- **Canonical repo:** https://gitlab.com/sat-mtl/tools/splash (the old `github.com/sat-metalab/splash` URL is dead; a stale GitHub mirror exists at https://github.com/jing-interactive/splash). **Licence: GPL-3.0-or-later.**
- **Docs:** https://sat-mtl.gitlab.io/documentation/splash/en/ — tutorials (`tutorials/first_steps.html`, `tutorials/splash_configuration.html`, `tutorials/multi_projector_example.html`, `tutorials/calimiro_calibration.html`), explanations (`explanations/technical_information.html`, `explanations/best_practices.html`, `explanations/ui/calibration.html`, `explanations/ui/blender.html`), FAQ.
- **What it does:** Given a UV-mapped 3D model of the surface, it "semi-automatically" calibrates each projector (intrinsics + extrinsics), computes blending between projectors automatically, and has an experimental colorimetric calibration using a gPhoto DSLR. Built for fulldomes, also used on buildings and moving objects. Tested with 8 outputs on two GPUs in one machine; multi-computer is "planned".
- **Architecture (technical_information page):** object graph of `world`, `scene`, `window`, `camera`, `object`, `mesh`, `image`/`image_ffmpeg`/`image_v4l2`/`image_shmdata`/`image_ndi`, `filter` (optional custom GLSL), `warp`, `gui`, `python`, `queue`. One **World** process handles non-GL objects; one **Scene** process **per GPU** handles GL objects; they communicate via shared memory and ZMQ; global state is a replicated **Tree** that each Root mirrors. A `camera` = a virtual camera for one projector rendering to an offscreen FBO; a `window` = one OS window on one output, linked to one or more cameras. Best practice is **one window per GPU spanning all its projectors** (e.g. 3840x1080 at x=1920 for two side-by-side 1080p projectors) because extra windows add context switches. Display arrangement (no gaps, same refresh) is done in the OS (`arandr`/`nvidia-settings`), not in Splash.
- **Calibration (explanations/ui/calibration.html):** For each camera, pick a mesh vertex (wireframe mode) and shift-click where it lands on the real surface; ≥6 (tutorial says 7) point pairs; press C to run a least-squares fit of FOV/principal-point/pose minimising reprojection error. Points are stored with the project and are independent of the mesh, so you calibrate on a low-poly "calibration model" (vertices at known seam intersections) and swap in a high-res UV sphere later (multi_projector_example). Second and third projectors are aligned by matching the textured view to the already-calibrated projector then adding ≥5 more points. A per-camera **Warp** tab gives a Bézier lattice for post-calibration correction "as a last resort" — explicitly recommended for *inflatable domes* where the real surface deviates from the model.
- **Blending:** Ctrl+B computes a static blend map; Ctrl+Alt+B recomputes every frame (for moving objects). Per-camera `blendWidth` and `blendPrecision`. Blend weights are stored as **vertex attributes** on the mesh (requires OpenGL ≥4.3); i.e. blending is computed in 3D on the model from projector overlap rather than as 2D screen-space ramps.
- **Colour calibration:** `colorCalibrator` object: HDR captures of each projector, options `colorSamples`, `equalizeMethod` (0 average, 1 weakest projector, 2 max luminance), `imagePerHDR`, `hdrStep`; Ctrl+O calibrates camera response, Ctrl+P calibrates projectors.
- **Calimiro automatic calibration:** structured-light patterns shown one projector at a time, camera moved to several positions so each area is captured ≥3 times; output to `/tmp/calimiro_$PID`. Still "partial" and under development.
- **Blender add-on:** node tree (World, GPU, Window, Camera, Object, Probe, Mesh, Image, Gui) exports `configuration.json` + OBJ meshes (export with Forward=Y, Up=Z, metres, Z-up). A separate shmdata add-on streams live meshes into Splash.
- **Best practices page:** codecs must be **intra-frame** — MJPEG or Hap/HapQ/HapAlpha via FFmpeg (`-c:v hap -format hap_q -chunks 8`); "codecs with inter-frame compression are untested"; model in metres; subdivide quads (Splash triangulates and can skew UVs).
- **Source to read** [mirror, may be stale]: `src/graphics/camera.cpp`, `warp.cpp`, `window.cpp`, `object.cpp`, `filter.cpp`, `geometry.cpp`, `shaderSources.h` (all GLSL lives here), `virtual_probe.cpp`; `src/controller/colorcalibrator.cpp`, `controller_blender.cpp`, `controller_gui.cpp`; `src/mesh/`, `src/image/`, `src/core/` (Tree / Root / World / Scene). Blending and geometric-calibration code was not located in the mirror listing — grep the canonical GitLab tree for `blend` and `geometricCalibrator`. **[unverified exact file names for blend/calibration]**

### 1.2 MapMap (mapmapteam)

- https://github.com/mapmapteam/mapmap — **GPL-3.0**, Qt (qmake `mapmap.pro`) + GStreamer + OpenGL; 2D "paints" (video/image/colour/camera) mapped onto "mappings" (quad, triangle, mesh, ellipse per the project site; the README itself lists none). Fullscreen output window; `.mmp` project file **[unverified extension]**. OSC API is documented at https://github.com/mapmapteam/mapmap/wiki/OSC (`/mapmap/paint/opacity`, `/mapmap/mapping/visible`, `/mapmap/mapping/depth`, `/mapmap/play|pause|rewind`). Wiki also has "Video file formats". Dev branch active-ish (1666 commits, 320 open issues). Good reference for a Qt 2D mapper's data model (paint vs mapping separation) and for an OSC control surface.

### 1.3 ofxPiMapper (kr15h) — the cleanest small C++ reference implementation

- https://github.com/kr15h/ofxPiMapper — **MIT**. openFrameworks addon, Raspberry Pi focus. Modes: presentation / texture-mapping / surface-editing (projection mapping) / source-assignment. Surface types: triangle, quad (with optional perspective warping `p`), grid-warp (add/remove rows/cols), circle, hexagon.
- **Homography:** `src/Surfaces/QuadSurface.cpp::calculateHomography()` builds 4 src points from the mesh bounding box and 4 dst points from the dragged vertices, calls `HomographyHelper::findHomography(src,dst,_matrix)`, recomputes lazily when corners change, and applies it with `glMultMatrixf(_matrix)` around `mesh.draw()` with normalized tex coords. `src/Utils/HomographyHelper.cpp` solves the 8×9 system by Gaussian elimination with partial pivoting (h33=1) and packs the 3×3 into a column-major 4×4 as `{h11,h21,0,h31, h12,h22,0,h32, 0,0,0,0, h13,h23,0,1}` (z row/col zeroed). This is exactly the "homography as a 4×4 so the GPU does the perspective divide" trick a WebGL mapper should use.
- **Save format:** `src/Application/SettingsLoader.cpp` writes `surfaces.xml`: one `<surfaces>` per preset, each `<surface type=N>` with `<vertices><vertex><x/><y/>`, `<texCoords>`, `<source><source-type/><source-name/><source-loop/>`, `<properties><perspectiveWarping/>` or `<gridCols/><gridRows/>`. Media paths are stored as names relative to a media directory.
- Also read `src/Commands/` (undo/redo command pattern) and `src/Surfaces/GridWarpSurface.cpp`.

### 1.4 openFrameworks warp/blend addons

- **ofxWarp** (https://github.com/prisonerjohn/ofxWarp, also forked at d3cod3/ofxWarp) — **MIT**, port of Paul Houx's Cinder-Warping. Three warps: `WarpPerspective` (4 corners), `WarpBilinear` (control grid), `WarpPerspectiveBilinear` (corners first, then curvature). `WarpPerspective.cpp::getPerspectiveTransform()` is the same 8×9 Gaussian-elimination homography packed into `glm::mat4` with the z row `[0,0,1,0]`. `WarpBilinear.cpp::updateMesh()` interpolates mesh vertices from the control grid with **bicubic (Catmull-Rom-style `cubicInterpolate`) by default or bilinear when `linear=true`**, with edge extrapolation by reflection; `resolution` (default 16 px per quad, range 4–64) and `adaptive` mode. `WarpBase` holds the blend parameters: `edges` (vec4 L,T,R,B widths, public range 0–2), `exponent` (default 2.0 — Bourke's p), `gamma` (vec3, default 1), `luminance` (vec3, default 0.5), `brightness`; serialised to JSON as `{type, brightness, warp:{columns, rows, "control points"}, blend:{exponent, edges, gamma, luminance}}`. Shaders live in `example/bin/data/shaders/ofxWarp`. Note: `WarpBilinear::getMeshBounds()` has an apparent MIN/MAX typo on max-y **[observation from reading source]**.
- **ofxProjectorBlend** (https://github.com/jeffcrouse/ofxProjectorBlend, fork of Flightphase/ofxProjectorBlend by James George, additions by Marek Bereza) — permissive MIT-style notice. Renders the whole app into one wide FBO, then draws each projector's segment through a blend shader. `src/ofxProjectorBlendShader.h` contains the fragment shader: `curve = loc/extend`; lower half `lumCon * pow(2*curve, blePow)`, upper half `1 - (1-lumCon) * pow(2*(1-curve), blePow)`; then per-channel `pow(curve, 1/gamma.rgb)`; left/right/top/bottom distances computed against `blankout` and `overlap` vec4s; corners multiply two edge factors; blackout regions return black. This is the direct ancestor of TouchDesigner's `projectorBlend`.
- **ofxBezierWarp** (https://github.com/gameoverhack/ofxBezierWarp) — legacy-GL Bézier surface: `glMap2f(GL_MAP2_VERTEX_3,...)` with an N×M control grid, `glMapGrid2f`, `glEvalMesh2(GL_FILL,...)`; texture coords via a second 2×2 `GL_MAP2_TEXTURE_COORD_2` map; FBO `begin()/end()/draw()` pattern. Useful as a conceptual reference only (fixed-function). Licence in `LICENCE.txt` **[not read]**.
- Others surfaced: `julapy/ofxQuadWarp`, `nariakiiwatani/ofxMeshWarp`, `roymacdonald/ofxGLWarper`.

### 1.5 Keystone (David Bouchard, Processing)

- https://github.com/davidbouchard/keystone — **GPL-2.0-or-later** (header in `Keystone.java`). `CornerPinSurface(parent,w,h,res)` holds a `res×res` mesh; corners are control points; `calculateMesh()` uses JAI `PerspectiveTransform.getQuadToQuad()` + `WarpPerspective.mapDestPoint()` to place interior points, and `getTransformedCursor()` inverts it for mouse picking; `render()` emits textured `QUADS`. `Keystone.save()`/`load()` write `keystone.xml` (`<keystone><surface res x y w h><point i x y u v/>`); load applies to existing surfaces by index. p5.mapper (below) credits it.

### 1.6 ProCamToolkit / mapamok (Kyle McDonald, YCAM) and RoomAlive Toolkit (Microsoft)

- **ProCamToolkit** https://github.com/YCAMInterlab/ProCamToolkit — **MIT**. `mapamok` loads a COLLADA model, user clicks model vertices then their projected positions, solves projector pose+intrinsics with OpenCV `calibrateCamera` (≥6 points), and sets the GL projection/modelview to match. `ProCamSampleEdsdk/Libdc` project+capture Gray codes (Canon EDSDK or FireWire), `ProCamScan` decodes to a point cloud, `ProjectorGeometryCalibrate` outputs `.exr` displacement maps; `totalProjectors=2` enables two-projector scans. TouchDesigner's **CamSchnappr** is an adaptation of mapamok.
- **RoomAlive Toolkit** https://github.com/microsoft/RoomAliveToolkit — **MIT**. `ProCamCalibration/` (C#): each projector shows Gray codes, Kinect v2 colour cameras capture them, depth gives 3D points, Levenberg-Marquardt solves projector focal length + principal point and depth-camera poses; `lockIntrinsics` keeps intrinsics once solved on a non-flat scene; shared cameras chain projector groups; global optimisation closes cycles. Output `calibration.xml` ensemble (cameras/projectors with `hostnameOrAddress`, `displayIndex`, 4×4 pose). `ProjectionMappingSample` renders an off-screen *user view*, builds an **off-centre projection matrix from each projector's intrinsics**, and re-projects the depth mesh per projector with vertex/geometry shaders (`Shaders/`). Multi-projector only on one adapter; "beyond 3–4 projectors a distributed framework may be needed". `RoomAliveToolkitForUnity/` ports this to Unity.
- **OpenCV structured_light module** — `cv::structured_light::GrayCodePattern` (log2(W) column + log2(H) row patterns, plus white/black; `getProjPixel()` maps camera px → projector px). Tutorials: https://docs.opencv.org/4.x/dc/da9/tutorial_decode_graycode_pattern.html and `tutorial_capture_graycode_pattern.html` (fetch blocked this pass **[not read]**).
- **procamcalib** (Samuel Audet, JavaCV) — original Google Code project; mirror at https://github.com/361809948/javacv.procamcalib; "full geometric and color calibration of projector-camera systems", multiple cams/projectors, no global optimisation. Cite Audet & Okutomi, PROCAMS 2009.

### 1.7 Omnidome

- https://github.com/WilstonOreo/omnidome — **AGPL-3.0**, Qt/C++14 "Fulldome Projection Calibration Software Framework": canvases (dome, sphere, cylinder, box, planar), projector objects with position/FOV/throw, bicubic warp grid, blend masks, export of calibration/UV images **[feature list from memory + three-projection-mapper's credits; README read only covers the Windows build]**. ### 1.9 TouchDesigner (Derivative) — documented palette tools

Overview page: https://docs.derivative.ca/Projection_Mapping. Tools:

## 2. The MPCDI standard (VESA Multiple Projector Common Data Interchange)

- **Origin:** VESA MPAC (Multi-Projector Automatic Calibration) Task Group; **v1.0 published 23 July 2013**; **v2.0** added colour (3D LUTs, decode/correct/encode LUT pipeline, chromatic-aberration RGB warp example) — press coverage at https://www.tomshardware.com/uk/news/vesa-mpcdi-standard-2.0,29261.html and https://displaydaily.com/?p=24279. The spec PDF is VESA-member/paid; **I did not read the spec text** — details below are triangulated from implementers' docs.
- **Container:** a ZIP archive renamed `.mpcdi` containing `mpcdi.xml` plus referenced files. XML has `<display>` → `<buffer>` (the render canvas, `Xresolution/Yresolution`) → `<region>` (one per projector/output: `id`, `x,y,xsize,ysize` as fractions of the buffer, `XResolution/YResolution` in pixels) → `<frustum>` (3D profiles) and `<fileset>` per region referencing `<geometryWarpFile>` (PFM), `<alphaMap>` (PNG, `gammaEmbedded` attribute), `<betaMap>` (PNG), `<distortionMap>`, plus `<coordinateFrame>` and `<extensionSet>` (BrightSign, Dataton, Unreal, VIOSO docs).
- **Profiles (four):** 2D Media ("2d"), 3D Simulation ("3d"), Advanced 3D ("a3"), Shader Lamps ("sl") — names confirmed by Dataton and Scalable docs; the short XML tokens are from memory of the spec **[unverified]**. 2D Media: content is a flat canvas, regions are 2D sub-rectangles — this is what WATCHOUT and BrightSign implement. 3D/a3: regions carry frustums so a real-time engine renders per projector (nDisplay exposes `projection`/`cameraTransform`). Shader Lamps: warp onto an arbitrary 3D object (Scalable Atlas → TouchDesigner MPCDI TOP).
- **Geometry levels:** Level 1/2/3 describe how dense/accurate the warp is; WATCHOUT supports Levels 1–2 "with no grid-size limit"; BrightSign 4Kx42 only Levels 1–2.
- **Warp file (PFM, "portable float map"):** 3-channel 32-bit float image, one texel per **output** pixel (or a coarser grid), **R,G = normalised (u,v) in [0,1] of where to sample the input buffer** (forward UV map, MPCDI §3.6.2 per Gaia Sky and WATCHOUT docs); B unused; PFM is stored **bottom-up, little-endian flagged by a negative scale** per the PFM format convention **[origin/endianness unverified against the MPCDI spec; Gaia Sky's samples are big-endian]**. Unreal's explicit path adds a world `Scale` because 3D-profile PFMs hold XYZ positions in metres, not UVs.
- **Alpha map:** per-pixel multiplicative blend/intensity mask (1 or 3 channels, 8/16-bit PNG), with `gammaEmbedded` so the player knows how to linearise it (Unreal "Alpha Gamma = 1.0 for a linear mask"). Vendors bake colour-uniformity correction into a 3-channel alpha.
- **Beta map:** black-level lift map (adds light in non-overlap areas to match the stacked black of overlaps); gamma does not apply to beta (BrightSign). Without beta only alpha blending is applied (WATCHOUT).
- **Who writes it:** VIOSO (Integrate/Anyblend/6), Scalable (SDM, Atlas), domeprojection ProjectionTools, NestMap (domes), Christie/Barco/Norxe tool chains (Norxe Unify ingests per-projector MPCDI: PFM + PNG blend/black-level + XML).
- **Who reads it:** Dataton WATCHOUT (2D only; single pass warp+blend after compositing, sub-pixel), BrightSign players (2D, one region per player, `roVideoMode.SetMpcdi()`), Unreal nDisplay (all, via `.mpcdi` or explicit PFM), TouchDesigner MPCDI TOP, Pixera (load only), 7thSense Delta, Barco/Christie projectors, vvvv (on request), Gaia Sky (PFM only).
- **Open-source parsers:** none found as a standalone library; Unreal's `MPCDI`/`DisplayClusterWarp` plugin source (in the UE source tree) is the most complete open reader. **[no standalone OSS parser verified]**

## 3. Professional workflow and troubleshooting knowledge

### 3.1 Site survey and projector choice
- Measure: surface dimensions, possible projector positions (throw distance, height, offset), ambient light in lux at the surface, power/signal runs, audience sight-lines (shadows).
- **Throw ratio** = distance / image width; 0.5:1 short throw up to 2:1+ long throw; zoom lenses give a range. Short-throw lenses usually lack lens shift, so placement is less forgiving (HeavyM guides, https://www.heavym.net/projector-guide-throw-ratio-specs/). Use the manufacturer's calculator (ProjectorCentral has one per model).
- **Brightness:** Lightform's article (https://lightform.com/blog/2020/12/28) gives the practical method: lux on surface = lumens ÷ area (m²); e.g. 7.11 × 4 m = 28.4 m² → 5,000 lm ≈ 176 lx; aim for **≥5× the measured ambient lux**; prefer ANSI lumens; check colour lumens ≈ white lumens; contrast ≥10,000:1 matters more than lumens for black floor and for hiding the projector rectangle; dark/brick surfaces need 2–3× the lumens of white. Cinema-style targets in foot-lamberts (12–22 fL in a dark room) are the other common vocabulary.
- **Black level / contrast** is the limiting factor for invisible blends (Bourke; Christie's mechanical blinder kit page argues electronic black-level lift reduces contrast).
- **Lens shift** avoids keystone; **do not use the projector's digital keystone** when a mapper is in the chain — CamSchnappr and SOS both require it reset, because it resamples pixels before your warp.
- Avoid 1-chip DLP colour-wheel units if the audience will see fast motion (rainbow effect); laser/LED for lifetime and stable colour (Lightform).

### 3.2 Placement, mounting, shadows
- Place projectors as symmetrically as possible (same height, distance, tilt) so blend zones have similar pixel density and brightness (Isadora forum advice; SOS manual: four projectors at ~90° spacing, ~17 ft from a 6 ft sphere's centre, lens centre at equator height).
- Minimise shadows by projecting from above/behind the audience line; for objects, aim projectors so overlap zones fall where incidence angles are similar.
- Rigid mounts; SOS troubleshooting attributes weeks-later drift to bumped mounts and lamp warm-up; record every physical measurement (lens height, distance to centre, resolution) in the show file.

### 3.3 Signal and output configuration
- **EDID is the number-one failure mode.** Displays re-enumerate when a projector is off or an extender strips the EDID serial; Windows/macOS then reorder outputs and warps land on the wrong projector. Fixes, in order of reliability (https://community.troikatronix.com/post/54345): power-on sequencing and never unplugging while running (~90 %); inline **EDID emulators** per output cloned from the real projector (~99 %; must support the exact res/refresh, e.g. 4K60 4:4:4); custom uniquely-named EDIDs (Kramer PT-12 / Extron EDID 101V); pro GPUs (NVIDIA RTX A-series / AMD Radeon Pro) that manage EDIDs in the driver. Pixera: "set EDIDs **before** creating calibration files" (https://pixera.helpjuice.com/working-with-projectors/camera-based-calibration).
- **Single logical display:** NVIDIA Mosaic / AMD Eyefinity combine outputs of one GPU into one desktop sharing one clock; VIOSO: separate Windows displays "won't be synchronised and applications won't span". One fullscreen window across the Mosaic (also Splash's "one window per GPU"). Unreal: don't span Mosaic across GPUs.
- **Frame sync:** tearing between projectors = outputs not sharing a clock or buffers swapping at different times. Tiers (Unreal nDisplay sync page, Mechdyne): VSync off (max fps, tearing) → Mosaic/Eyefinity (one clock per GPU) → **framelock** (Quadro Sync / FirePro S400 daisy-chain, house clock) → **genlock** (external reference) → genlock + framelock with swap barriers. Software "Ethernet" sync still tears because of DWM/driver. Use Studio/Production drivers with Quadro Sync.
- **Bandwidth:** 4K60 8-bit needs ~14–18 Gbps uncompressed; HBR2 (DP 1.2, ~17 Gbps payload) carries one 4K60; HBR3 (DP 1.4, ~26 Gbps) one 4K60 uncompressed, two only with DSC; HDMI 2.0 = 18 Gbps = 4K60 4:4:4 8-bit. **MST hubs** share the host link: DP 1.2 hub → two 4K30; DP 1.4 without DSC → one 4K60 + one 4K30; DP 1.4 + DSC → two 4K60 (StarTech MST14DP122HD compatibility table). **[bandwidth math is standard figures, not from a fetched primary source]**
- **DisplayLink/USB graphics:** CPU-side compression, 100s of ms latency, dropped frames, HDCP issues — fine for a GUI monitor, not for a projector output (Tom's Hardware review, Plugable KB).
- **Matrox DualHead2Go/TripleHead2Go** (legacy) and **Datapath Fx4** split one big output into several; the OS sees one display, which sidesteps enumeration problems — still the go-to for laptops.
- **Capture/NDI/Syphon/Spout** feeding a mapper: Splash FAQ — check PCIe bandwidth and RAM channels for capture; MadMapper takes Syphon (macOS)/Spout (Windows) from Resolume etc.

### 3.4 Order of operations on site
1. Rig, power, cable; label outputs; set EDIDs/emulators; configure Mosaic/desktop; verify every projector shows its own identifiable test pattern (QLab/Resolume/TouchDesigner all have test cards; SOS uses labelled patterns).
2. **Warm up 15–20 min** before any alignment (SOS manual: image drifts while warming).
3. Projector menus: native resolution, same lamp/colour mode on all units (Epson: Color Mode = Multi-Projection), keystone off, lens shift to centre, **zoom then focus** at the centre of the surface (SOS: focus at the equator).
4. Rough physical aim with a full-frame pattern (SOS "Red Ball": one projector at a time, cover your zone, minimal overshoot).
5. Geometry: corner pin / calibrate each projector to the surface or model; **align grids across seams** (SOS: translate first, then scale, rotate only with a laser level; "meet in the middle"; toggle projectors to see who is wrong). Mesh/Bézier warp last and locally.
6. **Blend after warp** (WATCHOUT, Millumin forum): set overlap widths to the real pixel overlap, enable blend, tune gamma/power/luminance on 25/50/75/100 % white and a grey ramp; then black-level compensation on black.
7. Colour/brightness match: dim the brightest projector (Millumin), white-point RGB per output (WATCHOUT), or camera-based (Splash colorCalibrator, Panasonic ET-CUK10, Christie Mystique).
8. Save the show file at every step (SOS "save often; revert"), export per-projector masks/warps as images where the tool allows (Stoner displacement maps, QLab PNG grids, Resolume presets).
9. Rehearse cues with real content; motion and high contrast reveal blend errors that static images hide (WATCHOUT).

### 3.5 Blend maths (what every tool implements)
- Bourke 2004 (https://paulbourke.net/miscellaneous/edgeblend/): overlap x∈[0,1]; f(x) = 0.5(2x)^p for x≤0.5, 1−0.5(2(1−x))^p for x>0.5; left image uses 1−f; p=2 typical (p=1 shows a step); apply inverse gamma per channel f^(1/G), G≈1.8–2.2; 256 px overlap on XGA worked, 128 px did not; multiplicative mask drawn as a post-pass; assumes Lambertian surface. Resolume's Power = p, Luminance = the "a" mid-point term, Gamma RGB = G. ofxProjectorBlend/projectorBlend implement exactly this.
- Black level: overlaps are brighter in black because two "blacks" add; fix by lifting non-overlap black (Resolume Black Level Compensation; Epson Black Level → Color Adjustment then Area Correction; MPCDI beta map) or mechanically (Christie blinders).
- Typical overlap guidance: Resolume ≥15 %, WATCHOUT 10–20 %, MadMapper forum 20–30 %, Millumin 5–10 %, QLab users 100–300 px.

### 3.6 Common failure modes
- Projectors swapped after reboot → EDID (above). Warp fine but blend band visible → gamma wrong or overlap width ≠ real overlap (test at 50 % grey). Grid lines cross at top but meet at bottom → projector height/measurement wrong (SOS: re-measure, try ±1 inch). Content soft in overlap → focus set at the edge rather than centre, or digital keystone on. Judder → content fps not dividing display refresh (24 on 60 Hz), or VSync/DWM. Stutter at high res → inter-frame codec or disk too slow (Splash FAQ, Resolume forum). Textures misaligned on planar faces → quads triangulated with skewed UVs (Splash FAQ: subdivide). Vertex-tweaking a badly misaligned rig → tearing artefacts (SOS: redo the coarse steps instead).

## 4. Content production for mapped surfaces

- **Template/stencil workflow:** disguise's "UV map as content template": unwrap the surface model to a normalised UV layout, render it as a 2D image at a resolution whose aspect matches the UV map and whose pixel density ≥ projector density (example: 1080 px over 5 m = 216 px/m → 3698×1080 template); give that PNG to After Effects/Photoshop as a background layer; the finished video is applied as the screen texture and virtual projectors sample it, so **projector moves never require re-rendering**. MadMapper exports surface/output templates and Resolume uses the composition "as a painter's palette" with slices sampling regions; Stoner/Kantan export UV maps. The same idea for a sphere: author in **equirectangular 2:1** (Isadora forum, Dataton, alibaba vendor guides) or cube maps/fisheye (Bourke Magic Planet page), and let the mapper's UV-sphere do the projection.
- **Resolution:** at least the projector's native per output; Splash's table goes to 4096×4096@60 HapQ; Lightform maxed at 1920×1200. Wide canvases (e.g. 5760×1080) exceed H.264 level limits in many players — another reason for intra-frame codecs.
- **Codecs:** Intra-frame, GPU-decoded codecs are standard because playback engines scrub, loop, speed-change and run many layers: **Hap** family (https://github.com/Vidvox/hap, BSD-style; spec `documentation/HapVideoDRAFT.md`: Hap/DXT1, Hap Alpha/DXT5, Hap Q/scaled YCoCg DXT5, Hap Q Alpha, Hap Alpha-Only/BC4, Hap R/BC7, Hap HDR/BC6; optional Snappy second stage; chunked for multithreaded decode; FFmpeg `-c:v hap -format hap_q -chunks 8`); **Resolume DXV3** (https://resolume.com/article/67: GPU decoded, "no key-frames", Normal vs High Quality ≈2× size, alpha only if source has it, encode with Alley or Adobe plugins; acceleration only inside Resolume); **NotchLC** (https://notchlc.notch.one/: GPU decode, 12-bit luma + 8-bit chroma ≈ 10-bit, ~5:1, scrubbable, free Adobe plugin, SDK licensed, native in Pixera/disguise/TouchDesigner/7thSense/Watchout etc.); **ProRes/MJPEG** as CPU-decoded intra-frame fallbacks (Splash recommends MJPEG). H.264/HEVC are long-GOP: seeking means decoding from the last keyframe, and "mp4 was designed for forwards playback at nominal speed" (Resolume forum); acceptable for linear timeline playback in VPT-style players. Trade-off: DXV/Hap files are ~6× H.264 size.
- **Frame rate:** match or integer-divide the output refresh (60 Hz → 30 or 60 fps); never re-encode 30→60 (Resolume forum); 24p on 60 Hz = 3:2 judder (RTINGS).
- **Loops:** render loops with the first/last frame continuity in the authoring tool and verify in the player with speed changes; keep audio in a separate timeline cue or embed and let the player clock to audio — **[no primary source found this pass for loop-seam practice]**.
- **Playback engines:** Resolume, MadMapper, TouchDesigner, QLab, Millumin, Isadora, VPT, Splash (`queue` object, SMPTE master clock how-to), WATCHOUT, disguise, Pixera. All expose the mapping as a post-composite stage.

## 5. Spherical and inflatable objects

- **How many projectors:** one covers roughly the front half with heavy stretching toward the limb (andrewlogie.co.uk 2013; Troikatronix thread). "A complete 360 physical sphere requires 4 projectors" (Troikatronix). Bourke's iSphere design: four projectors each covering a 90° sector of a 360°×120° band, blends at ±45°, **poles not projected**; a 2011 variant uses **three** SXGA+ projectors with vertical lens shift — raising them improves north-pole coverage at the expense of the south (https://paulbourke.net/dome/isphere). SOS uses four at 90° spacing, ~17 ft from a 6 ft sphere, lens at equator height (https://sos.noaa.gov/support/sos/manuals/alignment/all/). So three projectors at 120° is a legitimate compromise: equatorial coverage is complete, pole coverage is partial and the top/bottom caps need masking or acceptance.
- **Mapping approach (two schools):**
  1. **3D model + virtual projector per real projector** (Splash multi-projector tutorial literally does a dome with three 1080p projectors and a low-poly calibration mesh; TouchDesigner forum: "each camera sees exactly the same pixels as each projector"; MadMapper 3D calibration; Isadora 3D Player + 3D Stage Orientation; WATCHOUT 3D mapping). Content is equirectangular/cubemap applied to a UV sphere. Blending then comes from projector overlap on the model (Splash vertex-attribute blend; CamSchnappr UV-overlap masks).
  2. **2D per-projector quads with circular/gradient masks** (MadMapper's own workaround since it does not blend 3D surfaces; acidfudge weather-balloon project with two projectors feeding MadMapper via Syphon from Resolume; "edge blend didn't need to be super accurate for abstract visuals"). Masks are gradients on Multiply quads, curved with mesh warp.
- **SOS alignment procedure** (best-documented sphere workflow): warm up 15–20 min; record ground-to-equator height, lens-centre heights, lens-to-centre distances in inches into the config; keystone off, native res, same lamp mode; Step 7 Red Ball (one projector at a time, cover quadrant, no cyan on the sphere, minimal wall overshoot, centre then expand); Step 8 Grid (white-on-red grid, laser level on the equator, Translate then Scale, Rotate only for levelling, fix P1/P2 and P1/P4 seams first, move each line half-way); Step 9 Vertex Tweaking (nine numbered vertices, order 4,6 → 1,3,7,9 → 2,8; only after it is nearly seamless, otherwise it causes tearing). Troubleshooting: lines diverge top/bottom → re-measure heights ±1 inch; drift over weeks → bumped mount. Expect 1–2 h first time.
- **Inflatables specifically:** the surface is not a perfect sphere and moves with pressure/airflow — Splash recommends its per-camera Bézier warp "for imperfect surfaces like inflatable domes"; keep blower constant during calibration; expect to re-touch after the object settles. Giant Inflatables case study (12 m sphere) exists but gives no projector data. **[no inflatable-moon-specific technical write-up with three projectors was found]**
- **Internal-projection globes** (Magic Planet, OmniGlobe, PufferSphere) use one fisheye projector in the base or two blended projectors (Elumenati), calibrated by a radial latitude→radius curve plus centre offset (https://paulbourke.net/dome/magicplanet) — a different problem from external mapping but the content formats (equirect/fisheye/cubemap) are shared.

## 6. Browser / WebGL mappers for comparison

- **maptastic.js** (https://github.com/glowbox/maptasticjs; maintained fork austince/maptasticjs, npm `maptastic@3`): zero-dependency CSS corner-pin. `updateTransform()` builds the 8×8 system `[sx,sy,1,0,0,0,-sx*tx,-sy*tx]`, `[0,0,0,sx,sy,1,-sx*ty,-sy*ty]`, solves, and writes `matrix3d(...)` with `transform-origin: 0 0 0`. Layouts (`id`, `sourcePoints`, `targetPoints`) auto-saved to `localStorage['maptastic.layers']`. Edit mode SHIFT+Space; arrow keys; solo/crosshair/bounds. Single window, no blending. Licence file present but not read **[unverified]**.
- **dommapper** (https://github.com/ericrav/dommapper): same CSS `matrix3d` idea for any element (p5/three canvas, iframe), handles, shift-multi-select, arrow nudging, localStorage keyed by element id. No licence file visible.
- **p5.mapper** (https://github.com/jdeboi/p5.mapper, MIT, TypeScript, p5 2.x): quads, triangles, Bézier shapes, LED lines; credits Keystone and Jenny Louthan's projection transforms; calibration save/load to JSON **[not confirmed]**.
- **three-projection-mapper** (https://github.com/bhoffmann93/three-projection-mapper, MIT, v0.1.0-alpha): the closest analogue to the user's app — perspective corner pin + inner grid warp (bilinear/bicubic, code adapted from **Omnidome**), SDF polygon masks with feather/invert, per-surface edge feather (full multi-projector blend on roadmap), image adjustments + ACES, test card, Tweakpane GUI, `ProjectorCamera` modelling throw ratio and lens shift, **multi-window: controller + projector windows synced over `BroadcastChannel` sending calibration only, each window re-renders**, multi-surface per output, localStorage autosave scoped by `appId`, JSON export on roadmap. Key files `src/ProjectionMapper.ts`, `MeshWarper.ts`, `glsl/vertex/bicubicGridWarp.vert`, `src/addons/UvRectEditor.ts`, `examples/multi-window`.
- **3map** (https://github.com/PureHacks/3map, MIT): experimental Node + PhantomJS screenshots → three.js textured regions, separate `source.html`/`output.html` windows; no persistence.
- **4mapper** (commercial, browser-based corner pin), **Mapping Matter** (disguise, browser-based 3D projector previs/simulation — https://www.disguise.one/en/insights/webinars/introduction-to-mapping-matter), **SpoutBrowser** (Chromium that exposes web content as a Spout source for Resolume/MadMapper), **lpmt** (Little Projection Mapping Tool, C++/OF, https://github.com/CinimoDY/lpmt).
- **Pattern worth noting for the skill:** every browser mapper so far does corner-pin via a 3×3 homography (solve 8 unknowns, pack into 4×4) and persists to localStorage; only three-projection-mapper has grid warp, masks, feathering and multi-window sync — and none implements Bourke-style gamma-corrected blends, black-level lift, 3D-model calibration (solvePnP/calibrateCamera), or MPCDI/PFM import/export. Those are the gaps where the user's app can differentiate, and the OF/TouchDesigner/Splash sources above are the implementations to port.
